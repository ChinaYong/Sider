# Sider 分组共用侧栏：任务交接

整理日期：2026-10-10。项目：`Q:\1Coding\Sider`，Windows / PowerShell。

## 先读这一页

**目标：让若干网页标签页共用同一个存活的 AI 侧栏页面，其他标签页可以有独立侧栏，也可以完全没有侧栏。切页只决定显示哪个原页面，并更新引用来源；扩展不管理 AI 聊天会话。**

用户进一步要求：侧栏不遮挡网页；标签栏和地址栏保持原宽度；仅网页内容区缩窄，网页按剩余宽度自动重排；尽量轻量、无感。

当前进度：

- 四种模式的纯关联模型、异步冲突处理、跨页预设身份契约已实现，但没有接入生产侧栏。
- 本次交接重新运行相关测试：**44 项全部通过**。
- 原生侧栏能维持同一个全窗口共用页面，也能与已有独立页面并存；测试过的 API 路径不能满足完整的按组显示、隐藏和实例归属转换。
- 持久扩展窗口加临时 Windows 辅助程序，已在本地测试页验证分组状态保留和窗口显隐，但悬浮遮挡不符合用户要求。
- 缩窄整个浏览器再拼接扩展窗口可以避免遮挡，但标签栏和地址栏也变窄，不符合用户要求。
- `chrome.debugger` 缩小单个网页视口已验证响应式重排；调试提示和连接限制不符合期望的无感体验。**当前建议排除它作为默认实现，不应把这个实验算作需求已解决。**

**尚无经过完整验证、同时满足所有条件的产品承载方案。当前任务是继续寻找或论证这样的方案，而不是重新设计 AI 会话管理。**

“未找到完整方案”不等于已经证明所有方案不可能。已有实验的“不支持”仅针对测试过的浏览器版本和操作路径。

## 1. 用户需求与职责边界

### 1.1 必须正确理解的使用过程

假设 A、C 是同一完整域名，B 是另一个域名，开启“同站共用”：

1. 在 A 打开侧栏，加载一个原 AI 网站页面。
2. 切到 C：同一个侧栏和 AI 页面继续存在、显示；预设勾选不变；引用变量的来源改为 C。
3. 切到 B：B 是正常没有侧栏的标签页，网页恢复可用全宽；A/C 的侧栏页面仍存活，只是不向 B 显示。
4. 返回 A 或 C：显示原来的页面，保持原生草稿、附件、会话及页面状态。
5. 如果 B 原本有自己的独立侧栏，则恢复 B 自己的实例，不覆盖或合并它。

这里的“分组”是侧栏关联的逻辑分组，不必先创建 Chrome 原生标签组；用户没有要求新增复杂的标签组管理界面。

### 1.2 薄增强层

扩展负责：提示词构造、当前来源读取、预设勾选、扩展生成材料的追加/发送，以及侧栏实例与来源页的关联。

AI 网站负责：聊天会话、原生输入框、网站附件、发送、生成、聊天历史和页面内部状态。扩展保留原页面，让这些状态自然保留。

不要新增以下系统作为“解决方案”：

- 扩展自己的 AI 会话数据库、聊天历史同步或原生附件恢复系统。
- 重开同一聊天 URL、复制草稿、同步多个网页副本来冒充同一实例。
- 切页时销毁并重建 AI iframe，之后声称状态可以补回来。

代码里 `PanelSession` / `sessionId` 表示侧栏页面实例记录，不是 AI 网站的聊天会话。必要时可改善命名，但不能据此扩大产品职责。

### 1.3 最新显示约束

- 不接受侧栏窗口遮住网页内容。
- 顶部标签栏、地址栏保持原宽度，只让网页内容区缩窄。
- 网页根据实际剩余宽度排版，包含响应式断点、`100vw`、固定定位和读取视口的 JavaScript；仅压缩正文宽度不够。
- 没有关联的标签页不应保留空白侧栏或无用占位。
- 关注资源占用，不为每个来源标签页复制一个 AI 页面。

用户质疑 `debugger` 方案是否仍然不可用。上一轮结论是“对本项目的默认体验不合适”，并非“普通扩展无法申请 debugger 权限”，也不能擅自把用户的质疑写成接受调试提示上线的授权。

## 2. 四种模式和关联规则

模式设置全局生效，各浏览器窗口分别管理侧栏；默认“始终独立”。下表只针对目标页没有打开的侧栏关联时：

| 模式 | 切到目标页 | 固定开关 |
| --- | --- | --- |
| 总是共用 `shared` | 承接本窗口最近实际使用、仍打开的实例 | 不显示 |
| 始终独立 `independent` | 保持关闭；主动打开才创建独立实例 | 不显示 |
| 同站共用 `same-site` | 承接本窗口完整域名匹配的最近打开实例；无候选则关闭 | 不显示 |
| 手动控制 `manual` | 承接本窗口固定实例；无固定对象则关闭 | 显示 |

优先级和不变量：

1. **目标页已有打开关联时，始终恢复原实例。** 自动规则和设置变化都不能覆盖它。
2. 候选按最近实际使用选取。后台消息、来源刷新、导航不能提高使用顺序。
3. 更改模式仅影响后续关联，不合并、拆分、关闭或重载已经打开的实例。
4. 每页最多关联一个打开实例；同一个实例可以关联多页；不跨窗口自动共用。
5. 同站按规范化 `URL.hostname` 匹配，忽略协议、端口、路径，区分子域名。域名不可读取时不猜测。

例：A、B 原本各有独立实例，改为“总是共用”，从 B 切到新 C，C 承接 B，A 的原实例保留。

固定和关闭：

- 在手动模式固定当前实例，不创建副本；每个窗口最多一个固定对象。
- 固定 A 后进入已有独立 B，显示 B；固定对象仍是 A，供未关联页面承接。
- 在另一个现有实例上开启固定，只替换固定对象，不关闭旧实例。
- A/B 共用，在 B 取消固定：原实例留给 B 独享，A 等其他成员解除关联；不影响其他独立实例。
- 关闭共用侧栏：关闭整个实例及全部关联，清除对应固定对象和候选。
- 离开手动模式清除固定标记，保留已建立关联；重新进入时默认未固定。
- 固定表示允许后续页面承接，不根据关联成员数量自动开启。

## 3. 来源、预设和跨网页追加

**后续用户澄清“侧栏维持时勾选不变”优先。** 不能切到 C 就用 C 的旧临时勾选覆盖正在使用的共用侧栏。当前来源身份与侧栏/AI 实例身份必须分开。

典型过程：A 追加正文 → 切 B → B 追加正文 → 写比较问题 → 一次发送。

- 沿用现有预设入口，不新增待引用清单。
- 追加匹配键是“预设 ID + 来源 tabId + 完整来源 URL”，每份材料另有独立快照 ID。
- A、B 使用相同正文预设时保留两份材料。回到同一来源重复追加，沿用“未编辑块可更新，已编辑块保护”。
- 扩展生成附件的归属、预览、重试、删除按快照 ID 区分；不能清理另一来源材料或用户自行上传的附件。
- 材料标明来源标题、URL、快照时点；已完成追加不随切页或发送重新取值。
- 发送时勾选的变量针对当前来源取值，不能改写其他来源已追加快照。
- 去重只适用于同来源、同材料，不能只按预设 ID 去重。
- 切页/导航使未完成的提取、追加和发送准备过期，保留已完成草稿块和附件。
- 权限不足、不支持或正在导航时不能回退读取上一页。
- 成功发送后清理本次发送对应的临时勾选和草稿记录，其他独立来源/实例的临时状态不受影响。

生产当前按来源 tab 存储勾选。未来要明确共用侧栏的勾选状态与来源缓存的边界，遵守上述后期澄清；这层映射、完整快照字段与清理流程尚未集成，不能把身份工具函数当成全部实现。当前不做存储格式迁移。

模型的重要机制：

- `sessions` 保存稳定侧栏实例身份；`tabs` 保存单页关联与来源；`windows` 保存活动页、固定对象、已确认显示状态和未完成意图。
- 期望关联与承载实际完成分离。异步响应使用窗口版本和请求 ID，过期结果不得提交。
- 每窗口串行承载操作；已有实例失败不能先清理，返回新页面身份不能算作共用。
- 临时不可见与明确关闭分开；最后一个成员关闭才结束无成员实例。
- 导航保留关联、更新域名并使旧来源过期；同站策略不因导航自动拆分已有实例。
- 标签移到另一窗口时不自动承接目标窗口候选；保留实例需实际存活证据。
- 后台重启用真实存活承载清单核对，存储记录不是原网页存活的证据。

未来桥接需保留“来源浏览器窗口”身份；若承载是独立扩展窗口，不能把扩展窗口自身的活动标签当成引用来源。

## 5. 承载与布局探索结果

以下关键实验均为独立 Chromium **148.0.7778.96** 和本地测试页。没有验收真实登录 AI 网站。不要直接推广为用户 Tabbit 当前版本或所有 Chromium 的行为。

### 5.1 Chrome 原生 sidePanel

| 测试路径 | 结果 |
| --- | --- |
| 全窗口共用实例跨标签切换 | 通过：原扩展页面、AI iframe、草稿、文件输入和本地模拟状态保持 |
| 全窗口共用与已有 tab 独立实例并存 | 通过：两个原实例都存活、可恢复 |
| 把相同 URL 配给 tab 或全局，试图转移已有实例 | 不支持：产生新页面；URL 相同不代表实例相同 |
| 对 B 设置 `enabled:false` 以隐藏已有全局实例 | 不支持：全局侧栏仍显示，仍占网页宽度 |
| 对没有独立侧栏的 B 调用 `close({tabId:B})` | 不支持：报告没有活动的 tab-specific 侧栏 |
| 关闭/禁用全局侧栏，再靠切页自动恢复 | 不支持：原页面销毁或不可用；等待 6.5 秒后自动 open 被用户手势限制拒绝 |
| 原生关闭按钮能否准确归类为整组关闭 | 尚未验证：只验证 API 关闭及其事件 |

关键区别：A/C 共用 + B 已有独立可以成立；A/C 共用 + B 真正无侧栏，是当前原生路径的关键缺口。

原生宿主内放多个持久 iframe，已验证可保留不同组状态；但即使内部全隐藏，原生宿主仍占宽度；关闭宿主会销毁这些页面，不能解决 B 的全宽要求。

### 5.2 持久扩展窗口 + Windows 辅助程序

思路：一个持久宿主保存每组一个 AI iframe，只切换当前显示组；一个小型 Windows 程序负责显示、隐藏和定位窗口，不参与 AI 业务。

纯 `chrome.windows.update` 方案：等待窗口动画后，最小化可以生效；恢复时有抢焦点或被主窗口遮住的问题。不要重复早期过快采样得出的“最小化完全不生效”结论。

临时 C# 辅助程序采用窗口所有者关系及不激活的显隐/定位；严格限定本次隔离浏览器 PID 和唯一窗口标题，不操纵日常浏览器。

已验证：A/C → 第一组，D/E → 第二组，B → 无侧栏；50 次额外切换，两个 iframe 各加载一次；第一组草稿、2 MiB 本地文件输入、预设勾选保留，来源随当前页变化。可以隐藏而不销毁，并避免主动抢走焦点。遮挡判断仅在测试窗口实际位于前台时有意义。

短时观测：浏览器进程数 13 → 13；辅助程序工作集约 26–28 MiB；5 秒空闲 CPU 增量为 0。这不是长期性能保证，也不是整套浏览器/真实 AI 网站的总内存。

没有安装常驻程序、注册表项或 Native Messaging。扩展事件到辅助程序的通信由测试驱动临时转发，正式部署流程尚未实现。

**该原型悬浮在网页上，会遮挡内容。用户不接受这种效果。**

### 5.3 浏览器整窗缩窄，再并排放扩展窗口

验证通过：浏览器窗口从 1100 缩为 700，右侧放 400 宽的持久扩展窗口；没有窗口重叠，网页真实视口从 1087 变 687，隐藏侧栏时恢复。两个 AI iframe 在切换中仍各加载一次。

**标签栏和地址栏也被缩窄，不符合用户最新要求，不能当成最终方案。**

### 5.4 只改网页根元素 CSS 留白

1100 宽测试视口中，把根元素宽度改为 700：正文正常换行，但 `innerWidth` / `100vw` 仍为 1100，850px 媒体查询不触发，固定元素仍在原右边界。

再加 transform 可以改变部分固定元素的包含块，但不能一并修正视口单位和媒体查询。不能宣传为通用、无侵入的响应式排版方案。

### 5.5 `chrome.debugger` 改网页布局视口

临时扩展调用 `Emulation.setDeviceMetricsOverride`：

- 窗口宽度保持 1100，网页 `innerWidth` 从 1087 改为 687。
- 普通块、`100vw`、右侧固定按钮均按 687 排列，双栏自动变单栏；100px 标尺仍是 100px。
- 点击和 A/B 切换通过，页面实例及草稿保留，加载次数均为 1；未设置的 B 保持原宽。
- 显式 `clearDeviceMetricsOverride` 可恢复布局。

限制：需要 debugger 权限和浏览器调试提示；开发者工具连接可能中断它。仅 detach 在本测试中没有恢复宽度，但测试同时存在 Playwright 调试连接，不能推广为普通用户环境结论。

完整浏览器窗口截图因 Computer Use 窗口识别错误未取得；保存的图片只有网页内容。窗口尺寸不变有 API 证据，但顶部及右侧留白未完成整体视觉验收。也未与持久侧栏窗口接合验证，不要声称完整方案通过。

**当前产品判断：不适合作为无感默认路线。** 不能通过隐藏调试提示的特殊启动方式把体验代价从验证中抹掉。

### 5.6 其他已探索方向

早期还检查了同文档与跨文档 iframe 移动、offscreen、Document Picture-in-Picture 等方向，未得到满足完整要求的显示/隐藏路径。同一文档内保留 iframe 与把它搬到另一标签文档不是一回事。重新探索时，应先提出能填补哪一项能力缺口，不要仅凭 API 名称宣称可行。
